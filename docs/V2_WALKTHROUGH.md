# 第二版代码与面试讲解

## 1. 先理解两张图

外层 `workflow.py` 仍负责主持人、政府方、反对党、总结、评审的固定顺序。轮次由代码控制。

当启用 RAG，政府和反对方调用 `simulation/rag_agent.py` 中的发言子图。内层节点只有 model 和 tools；模型可直接结束，也可查询后继续。这样既保留辩论秩序，又把资料查找交给 Agent 自主判断。

面试表述：**外层确定性工作流协调多角色，内层有预算的工具调用 Agent 负责证据检索。** 不把固定角色轮流生成误称为完全自主的 Agent 集群。

## 2. 从文档到检索

`knowledge/download.py` 仅在明确运行时下载来源清单中的报告。`knowledge/documents.py` 按 PDF 页或 Markdown 标题提取内容，再切分；元数据从提取阶段一直保留到最终引用。

`knowledge/store.py` 通过 LangChain Embeddings 接口调用 DashScope，再用官方 `RedisVectorStore` 存储向量。文档嵌入与查询嵌入使用同一个模型；中文查询能够检索英文资料。代码不把相似度直接当作事实可信度。

入库使用稳定片段 ID、文件指纹和配置记录。重复导入不重做文档嵌入。变更文件先写新片段，失败则移除本次新片段并保留旧版；成功才事务性删除旧片段并更新清单。其他项目的键不在操作范围。进程被强制终止仍可能留下未发布的片段，显式重建可清理；第一版/第二版均不承诺崩溃恢复事务。

## 3. 一次工具调用到底发生了什么

1. `speech_prompt` 注入角色职责、完整历史及已有证据。
2. `llm.bind_tools([search_local_documents])` 向模型提供工具参数定义。
3. 模型返回 `AIMessage`，其中 `tool_calls` 提供工具名、查询参数和调用 ID。
4. 子图 tools 节点调用 `ToolNode`，由 LangChain 解析参数并执行检索。
5. 工具结果作为同一调用 ID 的 `ToolMessage` 回到上下文。
6. 模型阅读片段后继续查询或形成最终发言。

模型只能调用提供的工具，工具只有检索能力。每次发言两次预算，重复查询缓存。超额请求也有 ToolMessage 回应，避免留下未配对调用；预算耗尽后的模型不绑定工具。图还设置递归上限，防止异常提供方无限循环。

每次发言创建独立子图状态，因此政府和反对方不共享内部工具协议消息；共享的是公开发言及本场证据。

## 4. 证据、引用和评审是三个层次

- 检索：返回候选片段。
- 引用校验：检查引用 ID 是否确实来自本场检索。
- 评审：模型判断片段是否支持论点、是否忽略样本局限。

存在引用不等于论证正确。比如研究对象是自愿参加试点的企业，就不能直接推出所有行业都适用。评审仍可能判断错误，所以真实验收需要人工逐条核对部分引用。

`evaluation/evaluator.py` 为 RAG 使用更严格的 `EvidenceEvaluation`，在原有四维评分之外要求 `evidence_comment`。胜负仍是整体判断，不求和决定。

## 5. 为什么工具完成就保存

外层节点只有发言结束才完成；如果只在外层更新时保存，工具已执行但生成失败的过程会丢失。因此子图使用 `on_tool_event` 回调，将工具日志和证据先交给 CLI 保存；外层完成后根据日志唯一 ID 去重。

保存的是可审阅记录，不是可恢复执行的检查点。状态 JSON 不含模型内部思维链或密钥。每个文件采用原子替换，但 JSON 和 Markdown 不是跨文件事务。

## 6. 建议的面试演示顺序

1. 展示来源清单和报告 PDF，说明物理页码。
2. 独立运行中文检索命令，查看英文证据与来源。
3. 执行三轮 RAG 辩论，观察模型选择的查询。
4. 找到发言中的引用 ID，对照结果里的片段和 PDF 页。
5. 查看评审是否指出研究局限。
6. 运行离线测试，演示未知工具、无效引用和超时仍可控。

可以解释的取舍：工具预算控制成本；完整历史适合本版最多五轮；保留原模式方便对照；Redis 独立索引隔离项目；测试用假模型控制协议和错误路径，真实模型用于验证最终效果。
